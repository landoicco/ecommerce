# 1. Rewrite the existing Flyway migrations for PostgreSQL

- **Status:** Accepted
- **Date:** 2026-10-15

## Context

The project moves from MariaDB to PostgreSQL (see [infra-plan.md](../infra-plan.md), Phase 0). Migrations `V1` to `V3` were written in MariaDB SQL (`AUTO_INCREMENT`, `DOUBLE`, `DECIMAL`), so they do not run on PostgreSQL as they are.

The project rule is to never edit an applied migration, because Flyway stores a checksum per version and any environment that already ran the old file fails validation. That rule protects shared databases. Here, though, these migrations were only ever applied to throwaway local databases: nothing has been deployed, and no environment holds data worth keeping.

Two other things came up while doing this:

- With Spring Boot 4, Flyway's auto-configuration lives in `spring-boot-starter-flyway`. The project only had `flyway-core`, so the migrations were not running at all.
- Tests used H2 in MySQL mode with Flyway disabled and `ddl-auto=create-drop`, so the migrations were never exercised by the build.

## Options

1. **Keep `V1`–`V3` and add a `V4`** that converts the schema. It is not possible: the earlier files already fail on PostgreSQL, so `V4` would never be reached on a fresh database.
2. **Squash everything into a new baseline `V1`.** It gives a cleaner history, but it hides how the schema evolved and the file would soon be replaced by the fonda domain anyway.
3. **Rewrite `V1`–`V3` in place in PostgreSQL syntax**, with the same versions and the same intent.

## Decision

Option 3. `V1` and `V3` are translated (`GENERATED BY DEFAULT AS IDENTITY`, `NUMERIC`, `DOUBLE PRECISION`). `V2` is valid on both engines and stays as it is.

Alongside it:

- Add `spring-boot-starter-flyway` and `flyway-database-postgresql`.
- Replace H2 with Testcontainers running the same `postgres` image as `docker-compose.yml`. Flyway stays enabled in tests and Hibernate runs with `ddl-auto=validate`, so every build checks the migrations against the real engine and against the entities.

## Consequences

- Local databases created with the old MariaDB migrations are not reusable. That is acceptable, because the database container changes engine anyway.
- From the first deployment on, the rule is absolute again: changes go in a new `V{n}`, never into an applied file.
- Tests need Docker. It is available on the GitHub-hosted runners, and the first local run is slower while the image is pulled.
- An engine-specific bug (SQL syntax, types, JPQL that behaves differently) now fails the build instead of showing up after deployment.
